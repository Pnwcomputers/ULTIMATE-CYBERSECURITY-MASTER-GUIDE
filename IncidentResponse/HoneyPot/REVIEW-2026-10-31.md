# Review: Honeypots, Wireless IDS, Wazuh and Repository Integrity

_Review date: October 31, 2026, Pacific time (CI may be UTC November 1)._

## Scope and limits

This review deeply covers PR #141's Kismet, nzyme, DIY honeypot, ESP32, Wazuh, Python, systemd and README changes plus available **repository-wide** automated regressions. It is not a claim of exhaustively auditing every historical script, every dependency, every URL, or every hardware model in the entire repository.

## Reviewed and improved

1. Corrected claims that every honeypot hit is malicious; scanners, monitoring and authorized exercises also make contact.
2. Removed an executable remote curl-to-shell example and unrestricted passwordless sudo recipe from the T-Pot guide. Review and pin its installer before running.
3. Pinned the new GitHub Actions checkout/setup-python dependencies to SHA commits and disabled persisted checkout credentials, matching existing repo hardening standards.
4. Added specific Wazuh rule IDs for Kismet, nzyme, OpenCanary, Cowrie, DIY HTTP and serial ESP32 telemetry, with synthetic fixtures and tests. Exact manager rule semantics must still be validated in wazuh-logtest.
5. ESP32 custom UART reporting is clearly identified as a proposed firmware contract; it is not claimed to be supported directly by stock NanoC6, ShadowSentry or HoneyMire firmware.
6. Documented ShadowSentry's HTTP management/credential-capture risk and HoneyMire's locally bypassed dashboard authentication claim. Both require isolated management and data privacy controls.
7. Distinguished genuine over-the-air Wi-Fi captures from correlated Kismet/nzyme/ESP32 alerts; neither event timing nor reported MAC/BSSID alone authenticates a transmitter.
8. Added reciprocal links through Honeypots, IncidentResponse, Wireshark/deauthentication, Kismet/nzyme, Wazuh, and the root README.

## Outstanding existing repository blocker

The broader hardening test suite expects **Scripts/tool_pins.conf**, but this file is absent from GitHub. The repository's wildcard *.conf ignore rule likely prevented historical generated pins from being committed, though the cause is not proven. The original tool pins contain release SHAs, version numbers, and artifact hashes: do not invent them to manufacture a green test.

Track remediation in **[issue #142](https://github.com/Pnwcomputers/ULTIMATE-CYBERSECURITY-MASTER-GUIDE/issues/142)**: independently verify each pin, narrowly exempt this file from ignore, commit the actual verified values, and rerun the hardening tests. This is not a honeypot runtime failure, but it prevents an honest claim of passing all repo-wide code regressions.

## Checks before real deployment

- Confirm supported monitor radio/channel and Kismet API permissions; run each Wazuh XML rule through manager-side wazuh-logtest.
- Confirm nzyme machine event_type names on the actual installed version before enabling explicit severity mappings.
- Compare decoy events with known authorized scanners and the AP/controller's verified logs.
- Keep Pi/VM/ESP32 decoys on separate VLANs; validate deny-by-default egress from inside each device.
- Restrict credentials, attacker session transcripts, captures and payload files; test rotation, retention and quarantine.
- Build dashboard visualizations only after verifying indexed fields on the actual Wazuh version.
- Run the normally scheduled/manual **full online external link sweep**. The PR link gate is offline only; anti-bot/429 responses do not necessarily imply a broken URL.
