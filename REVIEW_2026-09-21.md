## Findings

### R01 — P1: Hardware storage test overwrites and deletes an existing file

**Location:** `HardwareTesting/py/full_hw_suite.py:268`, cleanup at line 274.

`StorageTest.run()` uses the fixed filename `testfile.fio` in the caller's current
directory. The benchmark writes into that path and then deletes it. There is no
ownership or pre-existence check. Even if fio fails, the cleanup removes any
pre-existing file with that name. The documented invocation uses sudo.

**Verified:** in a temporary directory, create `testfile.fio` containing a sentinel,
replace the instance's `run_cmd` with a no-op, then invoke `StorageTest.run()`.
The sentinel disappears even though no benchmark ran. No real disk test was run.

**Fix:** create a uniquely owned temporary directory on the filesystem being
tested; use its absolute filename and clean up only that directory. Add a regression
test proving an unrelated `testfile.fio` survives failure as well as success.

### R02 — P1: Cross-distro installer performs unsupported Arch partial upgrades

**Location:** `Scripts/pnwc_install_tools.sh:114`, followed by line 133.

The Arch-family branch refreshes repositories using `pacman -Sy --noconfirm` and
then installs individual packages using `pacman -S`. On a system with outstanding
updates, this can mix newly installed libraries/packages with older installed
components. The same path is selected for Arch, Manjaro, and BlackArch.

**Evidence:** static control-flow review; no package-manager commands executed.
Arch explicitly documents this sequence as unsupported in its
[system-maintenance guidance](https://wiki.archlinux.org/title/System_maintenance#Partial_upgrades_are_unsupported).

**Fix:** require a successful full system upgrade before installing from refreshed
metadata, or stop and direct the operator to complete it. Do not silently perform
an unannounced system upgrade as a side effect of a small tool selection.

### R03 — P1: OSINT playbook promises an automated workflow that is a scaffold

**Location:** `OSINT/Playbook/osint_investigator.sh:199`; claims in
`OSINT/Playbook/README.md:11` and its Features section.

The README advertises six investigation modules, case resume, SHA256 evidence
manifests, chain-of-custody logging, and report generation. The delivered script
only implements basic case creation and a DNS/WHOIS function. “Load Existing Case,”
“Investigation Menu,” and “Settings” print placeholder messages. The domain function
is not dispatched from the menu. The claimed end-to-end investigation cannot run.

**Verified:** read the complete 213-line script and compared its function/menu
dispatch with the README. Did not perform any external investigation.

**Fix:** immediately label the script as a prototype and document the functionality
that actually exists. Implement and test the missing workflow before restoring
claims about evidence integrity or generated reports.

### R04 — P2: AnythingLLM updates discard working artifacts before replacement succeeds

**Location:** `installer.sh:175`, `installer.sh:199`.

The AppImage downloads directly over its final filename. A failed or interrupted
transfer can replace a working installation with partial bytes. The engine updater
deletes the entire existing Ollama directory before attempting the replacement
download. Network failure therefore removes the previously working engine.

**Evidence:** static review of download/extraction order. No downloads or actual
installation were performed.

**Fix:** download into a sibling temporary location, validate the archive and
expected executable, extract into a staging directory, then replace the working
installation. Keep the old version available until the replacement is verified.

### R05 — P2: Missing optional engine dependency aborts desktop setup

**Location:** `installer.sh:192`, call at line 251.

When `zstd` is absent, `install_ollama_engine()` says it will skip the optional
engine, but returns 1. The top-level script uses `set -e` and calls the function
without handling failure. It exits before creating the desktop entry and AppArmor
profile. A download failure follows the same path.

**Evidence:** shell control-flow review. This is distinct from R04: it affects a
fresh desktop installation even when there is no existing engine to preserve.

**Fix:** explicitly handle optional-engine failure and continue desktop setup, or
make the dependency mandatory and validate it before downloading anything. Test
the missing-dependency and failed-download cases using command stubs.

### R06 — P2: Hardware streaming runner ignores failed child exit status

**Location:** `HardwareTesting/py/full_hw_suite.py:129`.

When the output reader completes, the runner calls `proc.wait()` but discards its
return value. It returns only output lines and a timeout flag. Failed benchmarks
without a recognized error string can leave the shared error list empty.

**Verified:** `HardwareTester().run_streaming()` running a harmless Python process
that exits with status 7 returns `([], False)` and records no errors.

**Fix:** record and propagate nonzero exit codes independently of output parsing.
Also review timeout cleanup: terminating a `shell=True` parent does not establish
that all benchmark descendants have stopped. That secondary concern was inspected
statically, not exercised with hardware workloads.

### R07 — P2: NanoVNA parser accepts invalid measurements and reports success

**Location:** `SDR/nanovna/tools/s1pdiff.py:145`; verdict logic around line 513.

The parser accepts floating-point NaN values without validating finiteness. NaN
does not satisfy ordinary threshold comparisons, so invalid measurements can
produce a successful verdict and non-standard JSON numeric tokens.

**Verified:** create a temporary `.s1p` file containing:

```text
# Hz S RI R 50
144000000 nan 0
145000000 nan 0
146000000 nan 0
```

Comparing that file with itself using `diff --format json` exits 0, reports
`"verdict": "OK"`, and says `within tolerance on all checks`. Output metrics contain
`NaN`. All 14 existing regression cases still pass.

**Fix:** reject nonfinite frequencies, components, and reference impedances before
calculations; validate positive reference impedance and the frequency ordering
required by interpolation. Add malformed-input tests and serialize JSON strictly.

### R09 — P2: Script collection contains both unmarked legacy code and syntax defects

**Locations:** `Scripts/GO/bruteforce/cassbrute.py:26`,
`Scripts/GO/cloud/s3browse.go:57`, plus Python inventory in the appendix.

Of 125 Python files, 22 fail Python 3 parsing. Twenty-one failures are Python-2-style
print syntax; these should be identified as historical material rather than assumed
to be supported executable tools. `cassbrute.py` has a separate indentation error:
a statement interrupts a `try` suite before its `except`. It is not merely a
Python-version mismatch.

Of 12 Go files, `s3browse.go` fails parsing: it uses a colon in an `if` statement
where Go requires an opening brace. The next line also treats the header map as a
callable, so repairing the delimiter alone would not establish a successful build.

**Verified:** Python AST parsing without importing the collection; `gofmt -e`
without `-w` for Go. No offensive scripts were executed or modified.

**Fix:** separate maintained tools from archived examples, document supported
runtimes and dependencies, and enforce syntax checks for the maintained subset.
Do not recommend installing an obsolete interpreter as the general solution.

### R10 — P2: OpenCanary's primary installation path deliberately bypasses dependencies

**Location:** `IncidentResponse/HoneyPot/opencanary.md:124` and lines 139–155;
related installer pattern in `Scripts/pnwc_install_tools.sh:169`.

The main OpenCanary recipe installs globally as root with both
`--break-system-packages` and `--no-deps`, then discovers required dependencies by
repeated startup failures. The document acknowledges a venv alternative at line
158, but only after presenting the incomplete installation as its main path.
The general tool installer likewise overrides system Python protections for
multiple packages while describing its helper as “always user-safe.”

**Evidence:** compared instructions with the
[upstream OpenCanary installation guide](https://github.com/thinkst/opencanary/blob/master/README.md),
which uses a virtual environment. No packages installed. Individual dependency
combinations were not experimentally reproduced.

**Fix:** make the isolated environment the complete primary recipe, resolve the
declared dependencies together, and use its executable paths in service units.
Keep historical troubleshooting clearly separated from recommended installation.

### R11 — P2: CI omits existing general CM5 and NanoVNA regression suites

**Location:** `.github/workflows/cm5-parrot-checks.yml:7` and line 31.

The only executable-test workflow is restricted to the Parrot script/test paths
and discovers only `test_cm5_parrot_setup.py`. Changes to the general CM5 setup
script or its tests do not trigger that workflow. The NanoVNA regression shell
script and the executable data-engineering labs are also absent from workflows.

**Verified:** inspected all four workflow files. Locally, both CM5 test modules and
the NanoVNA suite run successfully; the coverage gap is workflow configuration,
not a currently failing existing test.

**Fix:** add path-scoped jobs for both CM5 modules and NanoVNA, and a repeatable
runner for the documented data labs. Run fixture tests without requiring real
device access; explicitly expose any skipped root-dependent guards.

### R12 — P3: Earlier audit conclusions need clear revision scope

The report is dated August and records a clean-link assessment, says concerns are
not safety-critical, and describes several dedicated sections as missing although

outside its earlier conclusions.

**Fix:** label prior findings with the exact reviewed revision and link to the new
review. Reconcile the older expansion plan with the sections already added;
preserve historical evidence rather than retroactively claiming it was current.
